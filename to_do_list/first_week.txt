针对 CSW 这类合规筛查系统，要了解其业务和架构，核心思路是先通过“官方文档 + 关键人物访谈”建立顶层认知，再通过“系统周边信息 + 非核心代码”进行自下而上的验证。以下是你具体可以去哪里、找谁、看什么的详细路径。

一、业务与产品：了解“CSW 在做什么、为谁做、怎么做”
去哪里找、找谁问
信息来源	具体位置/对象	能获取什么
业务文档	Confluence/Wiki 中的 BRD（业务需求文档） 、用户手册、SOP（标准操作流程）	筛查场景、触发时机、人工调查工作流、上报规则
合规团队	合规官、AML 分析师、筛查调查员（Screener）	名单源、匹配阈值、误报处理、STR 上报流程
产品/BA	负责 CSW 的 BA 或产品经理	需求来源、优先级逻辑、业务规则变更历史
Jira/工单系统	CSW 相关的 Epic、Story、Bug 记录	历史需求、痛点、变更原因
监管文档	HKMA 通函、内部合规政策	名单更新时效要求、测试频率、审计要求
培训材料	内部 LMS、入职培训 PPT	业务术语、角色职责、系统操作流程
具体怎么看
1. 先画一张“筛查业务全景图”

从一笔交易进入 CSW 开始，到最终结论产出，逐环节确认：

触发点：是实时筛查（每笔支付/转账）还是日终批量？客户开户时是否也走 CSW？

输入数据：交易要素（付款人/收款人姓名、账号、金额、币种、国家）、客户画像（PEP 状态、风险等级）。

匹配逻辑：CSW 用的是什么匹配方式？精确匹配、模糊匹配（Fuzzy Matching）、音译匹配？阈值是多少？

名单源：当前接入了哪些名单？OFAC SDN、EU Consolidated、UN Sanctions、HKMA 本地名单、商业名单（如 Dow Jones、LexisNexis）？更新频率是多久？

告警路由：命中后告警如何分配？按风险等级、地区、业务线自动路由还是人工分派？

人工处置：调查员的完整工作流——查看告警 → 比对名单详情 → 判断真命中/误报 → 升级/关闭/上报。这个工作流的每一个状态和按钮，都是业务规则的外在体现。

上报与归档：STR 如何提交至 JFIU？审计日志保留多久？

2. 找合规团队做一次“业务 walkthrough”

请一位筛查调查员或合规官，用真实案例（脱敏） 走一遍系统：

“请给我看一个典型的真命中案例和一个典型的误报案例，从告警出现在队列里开始，到你做出最终判断，每一步你看到了什么、点了什么、依据什么规则。”

这是理解业务规则最快的方式。合规筛查系统的业务规则大量存在于调查员的判断逻辑中，文档往往不全。

3. 读历史变更记录

在 Jira 中搜索 CSW 相关的 Change Request 和 Bug，重点关注：

阈值调整的历史（什么时候调过？为什么调？调完后误报率/漏报率变化如何？）

名单源增删的历史（为什么加/删某个名单？监管要求还是业务需求？）

匹配算法变更（是否从精确匹配升级到模糊匹配？为什么？）

产出：CSW 端到端业务流程图、筛查类型矩阵、名单源清单、匹配规则与阈值说明、调查工作流状态图。

二、系统架构与上下文：了解“CSW 由什么组成、跟谁连、数据怎么流”
去哪里找、找谁问
信息来源	具体位置/对象	能获取什么
架构文档	Confluence 中的 系统上下文图、组件图、部署图	系统边界、上下游、技术栈
接口文档	Swagger/OpenAPI、WSDL、Postman 集合、接口目录	API 契约、字段、错误码
数据库	ER 图、数据字典、表结构（可只读访问）	名单表、筛查结果表、案件表、审计表
运维/生产支持	Runbook、监控 Dashboard、历史事件 RCA	监控指标、故障模式、升级路径
架构师/TL	系统架构师、技术负责人	设计决策原因、技术债、未来规划
非核心代码	入口层、集成层、配置、批处理、测试代码	调用链、配置参数、匹配逻辑的反推
环境信息	DEV/SIT/UAT/PROD 环境清单、发布记录	环境矩阵、版本管理、发布窗口
具体怎么看
1. 从“系统上下文图”开始，但不要只信文档

先找现有的系统上下文图，然后逐一验证：

CSW 的上游是谁？交易系统（核心银行/支付网关）如何把数据推给 CSW？是 API 调用、MQ 消息、还是文件投放？

CSW 的下游是谁？告警推送到案件管理系统（如 Actimize、Pega）还是内置案件模块？

外部依赖有哪些？名单提供商（OFAC、Dow Jones、Refinitiv）的数据如何进入 CSW？是 API 拉取还是文件导入？

有没有被忽略的依赖？比如搜索引擎（Elasticsearch 用于模糊匹配）、规则引擎、缓存、调度器？

2. 画一张“数据流图”

从数据入口到出口，逐段确认：

text
交易系统 → [API/MQ/文件] → CSW 数据摄取层 → 名单加载/索引 → 匹配引擎 → 告警生成 → 案件队列 → 调查处置 → 审计日志/上报
每一段都问三个问题：

数据格式是什么？ （ISO 20022、SWIFT MT、JSON、XML？）

传输方式是什么？ （同步 API、异步 MQ、批量文件？）

失败怎么办？ （重试、降级、人工补录？）

3. 从“非核心代码”反推架构

你目前能看非核心代码，这是验证架构文档的最佳路径：

看什么代码	能反推出什么
入口层（Controller/API Gateway）	CSW 暴露了哪些端点、请求参数、路由规则
数据摄取层	名单文件解析逻辑、字段映射、OFAC XML/CSV 解析方式
集成层（Client/Adapter）	上游系统如何调用 CSW、下游如何接收告警
配置（application.yml/properties）	匹配阈值、名单源开关、超时设置、Feature Flag
批处理/调度	名单同步定时任务、日终批量筛查任务、索引重建任务
测试代码	匹配场景的预期输入/输出——这是理解核心匹配逻辑的最佳替代路径
日志配置	筛查日志字段（请求 ID、匹配分数、命中名单、耗时）
4. 找运维/生产支持做一次“Runbook walkthrough”

请生产支持同事带你走一遍：

监控看什么：CSW 的 Dashboard 上有哪些指标？API 超时率、名单同步状态、告警队列深度、匹配耗时？

什么情况会告警：名单源同步失败、筛查引擎不可用、告警队列堵塞？

出了事怎么办：名单更新失败的 Runbook 是什么？筛查引擎故障时是否降级为人工补筛？

最近一次事件是什么：RCA 文档在哪里？根因是什么？行动项完成了吗？

5. 访谈架构师/TL，问“为什么”

文档告诉你“是什么”，架构师告诉你“为什么”：

为什么选择当前的匹配算法？有没有评估过其他方案？

为什么名单源是这个组合？有没有监管要求驱动的名单？

当前架构最大的技术债是什么？如果重来会怎么设计？

未来 6-12 个月的架构演进方向是什么？

产出：CSW 系统上下文图（验证版）、组件架构图、部署图、数据流图、技术栈清单、接口目录、调用方清单。

三、关键动作清单
优先级	动作	找谁/去哪	产出
P0	找合规官/调查员做业务 walkthrough（真命中 + 误报各一例）	合规团队	端到端业务流程图、工作流状态图
P0	收集现有架构文档并逐一验证	Confluence、架构师	验证后的系统上下文图、数据流图
P0	申请名单数据库只读权限，看表结构	DBA/运维	名单表、筛查结果表、案件表结构
P1	读 Jira 中的 Change Request 和 Bug 历史	Jira	阈值变更史、名单源变更史、痛点清单
P1	读非核心代码：入口层、集成层、配置、测试	代码仓库	模块地图、配置参数清单、匹配逻辑推断
P1	请运维走 Runbook（监控、故障、事件）	生产支持	监控清单、Runbook 摘要、事件台账
P2	访谈架构师，问设计决策和技术债	架构师/TL	设计决策记录、技术债清单
P2	读合同中的 CSW 条款（SLA、知识转移、退出）	vendor manager/法务	合同摘要、vendor 绩效指标
一句话总结：业务靠“合规团队 walkthrough + Jira 变更史”，架构靠“文档验证 + 非核心代码反推 + 运维 Runbook 走查”。先建立顶层认知，再用代码和运维细节逐层验证，最后用架构师的“为什么”把碎片拼成完整的图景。
