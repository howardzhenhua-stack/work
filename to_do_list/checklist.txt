一、业务与产品
CSW 的核心业务是：对银行每笔交易或转账，基于规则和黑名单进行合规调查。

□ 筛查类型清单：确认 CSW 覆盖哪些筛查场景——制裁名单筛查（Sanctions Screening）、政治公众人物（PEP）、负面新闻（Adverse Media）、监管执行名单（Regulatory Enforcement Lists）、声誉风险（RRE）等。
□ 筛查触发时机：是实时筛查（每笔交易/转账），还是批量/日终筛查？是否包含客户开户时的首次筛查（Onboarding Screening）以及持续监控（Ongoing Monitoring / Continuous Monitoring）。
□ 名单覆盖范围：当前系统接入了哪些名单源——OFAC SDN、OFAC Consolidated、EU Consolidated、UK OFSI、UN Sanctions List、HKMA 相关名单等。
□ 匹配规则与阈值：匹配算法是什么（精确匹配/模糊匹配/Fuzzy Logic）？阈值（Threshold）如何配置？哪些分数区间触发自动拦截、人工审核或放行。
□ 人工调查工作流：从告警生成 → 路由分配 → 调查员处置 → 升级 → 关闭/上报（STR/SAR）的完整状态机。
□ 上报与监管接口：可疑交易报告（STR）如何提交至 JFIU？制裁违规如何上报？是否有监管报送的自动接口。
□ 术语表：PEP、RRE、REL、POI、INS、SDN、OFSI、UNSCR 等合规术语的准确定义和系统内使用方式。
产出：CSW 端到端业务流程图、筛查类型矩阵、名单源清单、匹配规则与阈值说明、调查工作流状态图。

□ 系统上下文图：CSW 的上游（交易系统、核心银行、客户开户系统、支付网关）、下游（案件管理系统、上报系统、数据仓库）、外部名单源（OFAC、EU、UN、HKMA 等）。
□ 组件架构：CSW 内部组件划分——数据摄取层（Data Ingestion）、名单加载与索引层（Index Loading）、筛查与匹配引擎（Screening & Matching Engine）、告警与案件管理（Alerting & Case Management）、安全与审计（Security & Audit）。
□ 部署架构：CSW 部署在哪些环境（DEV/SIT/UAT/PROD），是否容器化，数据库/中间件/消息队列的技术栈。
□ 数据流图：交易数据 → CSW 输入 → 筛查匹配 → 告警输出 → 调查系统 → 上报的完整数据流。
□ 技术栈清单：CSW 使用的编程语言、框架、数据库、消息中间件、规则引擎、搜索引擎（如 Elasticsearch 用于模糊匹配）。
□ 非功能需求：每笔交易的筛查延迟要求（SLA）、吞吐量、可用性、灾备方案、数据保留期限。
产出：CSW 系统上下文图、组件架构图、部署图、数据流图、技术栈清单。

三、接口与契约
CSW 作为筛查引擎，接口是理解其行为的关键。

□ 筛查 API 契约：CSW 对外暴露的筛查接口（如 /match 或 /screening），请求字段（姓名、别名、DOB、国籍、证件号、交易号等）和响应字段（匹配分数、命中名单、命中实体 ID、案件编号）。
□ 名单更新接口/数据源：名单数据如何进入 CSW——是批量文件导入（OFAC XML/CSV）、API 拉取（OpenSanctions API），还是定时同步？同步频率和失败处理机制是什么。
□ 案件管理接口：CSW 与案件管理系统之间的接口——告警推送、调查结果回写、状态同步。
□ 上报接口：STR/监管上报的 API 或文件接口规范。
□ 错误码与异常处理：筛查超时、名单源不可用、匹配引擎故障时的错误码和降级策略。
□ 幂等与重试：同一笔交易重复提交时，CSW 如何保证幂等？筛查失败后的重试/补偿机制。
□ 接口调用方清单：哪些系统调用 CSW、调用频率、峰值 TPS。
